## 3. T5.3 测试驱动迭代：问题发现与修复

M5 测试过程共发现并修复 **8 项问题**（按严重度排序），每项均有「现象 → 根因 → 修复 → 验证」闭环。

### 3.1 【P0】FAISS 索引陈旧导致检索 0% 命中

- **现象**：重建 `db/app.db`（语料扩 5 领域）后首次跑检索评测，Top-5 命中率 0%。
- **根因**：`VectorStore.ensure_ready()` 只校验索引维度/后端，不校验 DB 是否变化；磁盘索引是重建前的陈旧快照（169 向量 vs 库内 270 分块），chunk_id 整体错位，全部命中无效 chunk。
- **修复**：`api/core/vector_store.py` 增加索引签名（分块数 + 最大 chunk_id + 维度 + 后端），持久化到 `faiss_meta.json`；`load()` 校验签名，不一致即自动重建（`build_from_db`）。
- **验证**：重启后端日志 `rebuilt index: 270 vectors`；测试集命中率 88.9% →（叠加 3.2 后）100%。

### 3.2 【P1】重排缺风格信号，两个测试集任务未命中

- **现象**：测试集 2 个未命中（E117 教育·犀利 / E132 科技·犀利），查询均明写「以「犀利」口吻」，召回的却是同领域「轻松/专业」素材——领域对、风格错。
- **根因**：`rerank()` 只有同领域加权（+0.15），无同风格信号；`fetch_chunks` 早已带出 `styles` 字段但未被使用。
- **修复**：`api/core/rerank.py` 新增 `_detect_style()`（从查询识别 专业/轻松/犀利）与风格加权（+0.12）；`rerank()` 增加 `style` 参数，调用方显式提示优先、查询自动识别兜底；`rag_pipeline.retrieve()/generate()` 透传 `spec["style"]`。
- **验证**：E117/E132 均命中；全量 180 条 100%。

### 3.3 【P1】召回池 20 条装不下 5 领域语料

- **现象**：E117 的同领域同风格素材在粗排第 29/30/45/48 位，20 条池根本捞不到。
- **根因**：查询模板词（「为 XX 领域账号在 XX 渠道以 XX 口吻产出…」）占字符主体，稀释了领域信号；语料从 3 领域 54 篇扩到 5 领域 90 篇后，单领域素材的粗排密度下降。
- **修复**：`config.RECALL_TOP_K` 默认 20 → 40（FAISS 暴力检索，零额外成本）。
- **验证**：E117 进入候选池并经风格加权重排进 Top-5。

### 3.4 【P2】评测脚本与生产口径漂移

- **现象**：`eval_retrieval.py` 内嵌 `RECALL_TOP_K` 兜底值 20、自行拼装「粗排+重排」逻辑，与生产 `rag_pipeline.retrieve()` 是两份实现——生产改了评测不知道，评测数字失去证明力。
- **修复**：评测改为直接调用 `rag_pipeline.retrieve()`（生产同路径），`RECALL_TOP_K` 从 `config` 导入；透传任务的 domain/style 提示，与 generate 链路同参数。
- **验证**：评测日志「粗排40→重排5」与生产一致；全量复跑 100%。

### 3.5 【P2】素材搜索端点绕过两阶段检索且缺账号隔离

- **现象**：`GET /api/materials?q=` 的语义检索直接 `store.search(k=5)`，不过重排、不带领域/风格提示——与 M3 文档宣称的「粗排→重排」不符；且该路径未按 `user_id` 过滤，存在跨账号可见其他用户素材的越权风险。
- **修复**：`api/routers/materials.py` 改走统一 `retrieve()`（k=min(max(limit,5),20)），结果按 `user_id` 过滤；LIKE 兜底移除 `content LIKE`（加密字段无法匹配，纯浪费）仅保留标题匹配，且排在语义结果之后不覆盖排序。
- **验证**：冒烟测试 `q=美妆/教育` 各 18 命中（含新领域）；登录 demo_seed 外无其他账号数据，隔离生效。

### 3.6 【P2】Mock 选题受众表缺新领域

- **现象**：美妆/教育领域 Mock 选题的 `target_audience` 掉到「泛兴趣人群」。
- **修复**：`rag_pipeline._mock_topics` 的 `aud_map` 补美妆（爱研究成分与妆效的年轻消费群体）、教育（关注孩子成长与自我提升的学习型家长/学生）。
- **验证**：选题生成冒烟输出受众正常。

### 3.7 【P3】文档计数与口径过期

- **现象**：108 条/54 素材/162 分块等旧计数散落在 M3 交付说明、评测方案、chunk_spec、data/README；M3 消融数字（70.4%→97.2%）是旧语料旧口径。
- **修复**：统一更新为 180 条/90 素材/270 分块；M3 文档中的消融数字加注「V1.1.0 语料口径」版本说明，避免与本次 180 条口径混淆。
- **验证**：全文检索无残留旧计数。

### 3.8 【P2】检索路径缺字段，前端「分块数」显示 0（第 5 章冒烟发现）

- **现象**：素材库仅**默认列表**正常显示「分块数=3」；一旦输入关键词走检索（`mode=search`），列表的「分块数」全部显示 0，且风险是用户误判素材未分块。
- **定位**：`api/routers/materials.py` 检索分支的两条 SELECT 只取 `id,title,domains,platforms,styles`，漏了 `chunk_count`/`created_at`；前端列渲染为 `v ?? 0`，字段缺失即渲染 0。默认列表分支的 SELECT 含这两个字段，故只有检索路径异常。
- **修复**：检索分支（语义结果回查 + 标题 LIKE 兜底）两条 SELECT 补齐 `chunk_count,created_at`，与列表分支字段对齐。
- **验证**：`GET /api/materials?q=美妆` 返回 `chunk_count=3`（修复前为缺字段）；第 5 章截图 `02_materials_search_meizhuang.png` 实测「分块数」列显示 3。

## 6. 已知限制与口径声明

1. **离线口径**：本环境无 LLM API Key、无 BGE 权重，embedding 为字符 n-gram 哈希、生成为 Mock 模板。因此 2.1 是「n-gram 向量 + 规则重排」口径、2.3 是「结构规则」口径——二者是**回归基线**而非最终语义质量。接入真实 LLM/BGE 后，`eval_retrieval.py` / `eval_generate.py` / `eval_adapt.py` 同命令重跑即为验收数据（eval_generate 检测到 `LLM_API_KEY` 自动切 LLM-judge）。
2. **检索兜底行为**：离线无语料向量时素材检索退化为标题 LIKE（content 加密无法 LIKE）——预期行为，非缺陷。
3. **消融数字不可跨版本直接比较**：3.1 修复前的 88.9% 与 M3 文档的 97.2% 分属不同语料规模（54 vs 90 素材）与口径，报告中均已标注。
