> 版本：V1.0.0 ｜ 日期：2026-10-12 ｜ 对应计划书 T5.4「AI 协作过程文档」
>
> 面向读者：想复用本项目协作方法的开发者 / 需要答辩「AI 辅助开发过程」陈述的团队成员。

## 1. 协作总原则

本项目 100% 的代码、文档、数据脚本均由 AI 在人类主导下产出。总结为一条主线：

> **提需求 → 提问澄清 → 确认方案 → 生成产物 → 审查 → 迭代优化**，每轮循环只推进一个可验证的小步。

三条铁律：

1. **禁止假设**：需求含糊点必须先提问确认，再动手（本项目因此纠正过领域词表、演示账号口径等多处隐患）；
2. **文档先行**：先 PRD/架构/数据库设计，后编码；文档是唯一事实源，代码与文档冲突时以评审结论为准并双向修正；
3. **可验证才交付**：每个交付物必须附带验证证据（构建通过、脚本实测、数字对账），不接受「应该可以」。

## 2. 协作工作流（六步循环）

```
① 提需求          人类用短指令描述目标（如「推进 M5」「把美妆/教育语料补上」）
      ↓
② 提问澄清        AI 列出含糊点与选项，人类拍板（AskUserQuestion）
      ↓
③ 确认方案        AI 输出任务分解 + 执行策略，人类确认后进入 Agent 模式
      ↓
④ 生成产物        代码 / 文档 / 数据脚本，遵循项目既有约定（见第 4 章）
      ↓
⑤ 审查            AI 自审 + 人类评审：按 P0/P1/P2/P3 分级列问题
      ↓
⑥ 迭代优化        分批修复 → 升版归档 → 更新项目记忆 → 进入下一循环
```

**关键机制**：

- **任务清单（TaskCreate/TaskUpdate）**：每个里程碑建任务、开工标 in_progress、完工即标 completed，进度对双方可见；
- **项目记忆（`.workbuddy/memory/`）**：跨会话沉淀约定（领域词表唯一真源、平台码、依赖环境坑），新会话开局即注入，避免重复踩坑；
- **版本化交付**：文档按 `V1.x.0` 文件名版本化，旧版进 `archive/`，审查报告记录每次升版差异。

## 3. 本项目实例：一次完整的协作循环

以「领域词表扩展」为例（2026-10-12），演示六步如何落地：

| 步骤 | 实际发生 |
|---|---|
| ① 提需求 | 人类：「把美妆/教育加进领域词表，后续可能继续增加邻域词，据此优化」 |
| ② 提问澄清 | AI 确认：是前端展示词表还是含生产数据？后续加词的频率与责任人？——人类明确「前端+数据都要，且以后会持续加」 |
| ③ 确认方案 | AI 给出「单一真源 + 自动补全」设计：`DOMAINS` 常量收敛 + Mock 数据自动覆盖新领域 |
| ④ 生成产物 | 改 `types.ts`/`mock.ts` → 36 篇语料 → `clean_chunk.py` 播种 → `build_eval_set.py` 扩维度 → 重建 `app.db` |
| ⑤ 审查 | 自审发现：`_gen_corpus.py` 才是语料唯一生成器（临时脚本要并入）、文档计数过期、`aud_map` 缺新领域 |
| ⑥ 迭代 | 修复 + 全量验证（tsc/build/播种/冒烟/180 条评测）→ 更新 4 份文档 + 项目记忆 + 工作日志 |

**可复用的经验**：把「以后还会变」的设计收敛到**唯一真源**（如 `DOMAINS`），让扩展只改一处——这是本次协作最有价值的设计决策。

## 4. 项目约定速查（AI 协作时必须遵守）

| 约定 | 值 |
|---|---|
| 领域词表唯一真源 | `frontend/src/api/types.ts` 的 `DOMAINS`（科技/生活/财经/美妆/教育）；新增领域同步 `data/clean_chunk.py` 的 `SEED_DOMAINS`、`build_eval_set.py` 的 `DOMAINS`、`data/corpus/` 语料 |
| 平台码 | `weixin`/`xhs`/`douyin`（传码不传中文名） |
| 风格标签 | 专业/轻松/犀利 |
| 演示账号 | `demo_seed`（口令见 `data/clean_chunk.py`，与 Login.tsx 提示一致） |
| 密钥 | `DB_FIELD_KEY` 在 `.env`，设定后不得更换 |
| 文档命名 | 按版本号 `XXV1.x.0.md`，旧版归档 `archive/` |
| 交流语言 | 中文；文档用 Mermaid 图表增强直观性 |

## 5. 与 AI 协作的提问技巧（本项目验证有效）

1. **给上下文而不是只给指令**：「推进 M5」前先确认计划书 5.2.5 的范围——AI 会先读计划书再动手，避免范围漂移；
2. **要求先方案后执行**：复杂任务先要任务分解与执行策略，人类确认再落码（Plan 模式思维）；
3. **要求证据链**：「验证通过」必须附命令与输出（构建日志、评测数字、冒烟结果），AI 会保留原始输出备查；
4. **分级报问题**：让 AI 按 P0–P3 列问题并分批修，避免一次改太多无法回归定位；
5. **及时纠正认知**：发现 AI 记错事实（如口令口径）时，用可验证的证据纠正，并要求同步修正项目记忆，防止错误跨会话传播。

## 6. 本项目用到的 AI 能力地图

| 能力 | 用在哪 |
|---|---|
| 文档撰写与审查 | PRD、架构设计、数据库设计、M1–M5 交付说明、测试报告 |
| 代码生成 | FastAPI 后端（14 端点 + SSE）、React 前端（六页）、数据脚本 |
| 数据工程 | 90 篇合成语料生成、清洗分块加密入库、180 条评测集构建 |
| 评测与调优 | Top-5 命中率从 88.9% → 100%（风格加权 + 召回池扩容 + 索引签名校验） |
| 工程排障 | FAISS 索引陈旧（0% 命中）根因定位、跨账号越权隐患修复、口令口径不一致追溯 |
| 性能优化 | 路由拆包 + vendor 分块：入口 1.05MB → 29KB |
| 安全审计 | 字段加密、JWT、CORS、口令一致性全链路核验 |

## 7. 常见坑与对策（来自本项目实战）

| 坑 | 对策 |
|---|---|
| AI「记错」项目事实（旧口令/旧计数） | 以代码/DB 为唯一事实源，程序化比对（哈希验证）而非肉眼核对 |
| 显示层对敏感字符串归一化，肉眼核查失真 | 用哈希/布尔结果做一致性校验，不依赖字面量展示 |
| 评测脚本与生产逻辑各写一份，口径漂移 | 评测直接调用生产函数（`rag_pipeline.retrieve`），「测的即用的」 |
| 环境依赖缺失导致「跑不起来」 | 受管 venv 统一装依赖，启动命令写进文档，禁止用错解释器 |
| 文档计数随数据演进过期 | 数据变更后全局 grep 旧计数，批量更新并在审查报告记录 |
| 临时脚本游离在正式产物外 | 生成逻辑并入正式脚本（`_gen_corpus.py`），保证可复现 |

## 8. 复现本项目的最小步骤

```bash
# 1) 读文档建立全局认知（顺序即依赖）
docs/PRD.md → docs/架构设计.md → docs/M3交付说明与API文档.md → docs/M4交付说明.md

# 2) 起全链路（见 docs/项目说明.md 模式 B）
python -m venv .venv && source .venv/bin/activate
pip install -r api/requirements.txt
python db/init_db.py && python data/clean_chunk.py --reset
uvicorn api.main:app --port 8000 &          # 后端
cd frontend && npm install && npm run dev    # 前端

# 3) 跑评测复现 M5 结论（阈值与实测见 docs/M5测试报告.md）
python -m api.eval_retrieval --split all
DEMO_BASE=http://127.0.0.1:8000 python -m api.eval_adapt
DEMO_BASE=http://127.0.0.1:8000 python -m api.eval_generate --split test --limit 0
```

---

**结语**：AI 协作的质量上限，取决于人类能否提供**清晰的上下文、可验证的标准和及时的纠正**。本项目的方法论可浓缩为：文档先行、唯一真源、证据交付、记忆沉淀。
